# Reverse-engineering plan: Igor: Objetivo Uikokahonia (Spanish CD-ROM)

## Purpose of this document

[REIMPLEMENTATION_PLAN.md](REIMPLEMENTATION_PLAN.md) describes the target ScummVM
engine and its milestones. This document is narrower and answers one question in
detail: **how do we actually recover the game's data and logic from the original
binary, in a way that is verifiable at every step, before committing to porting any
particular room?**

This matters because the single biggest risk in this project is not writing C++, it
is discovering three months in that some format or some room's logic cannot be
recovered from the tools at hand. This plan is written to retire that risk early,
format by format, with a runnable check for every claim. Every format below has
already been independently decoded and pixel/byte verified during this planning pass
(see [tools/igor_cd_extract/](tools/igor_cd_extract/) and its
[EXTRACTION_REPORT.md](extracted_cd/EXTRACTION_REPORT.md), regenerated by running the
tool) -- this is not a theoretical plan, it is a report on work already done plus the
plan for what is left.

## Version decision: start with the Spanish CD-ROM

Confirmed this session, directly against the files in this workspace:

- `IGOR-CD/IGOR.EXE` is exactly 9,115,648 bytes, matches the historical detector's
  size check for `kIdSpaCD`, and is a segmented NE ("New Executable") binary, **not**
  a Borland-overlay DOS binary. It requires no unpacking.
- `IGOR-CD/IGOR.DAT` is exactly 61,682,719 bytes and holds **only** speech/effects
  VOC audio, indexed by a separate flat offset table (`fsd_sp_cdrom.h`, 175 entries).
  It is irrelevant to graphics/logic reverse engineering.
- Every logical resource (backgrounds, palettes, masks, area tables, room text,
  sprites, action/dialogue blobs) the historical `create_igortbl` tool catalogued for
  the CD release resolves to a byte range **inside `IGOR.EXE`**, confirmed against
  the live file (see "Confirmed proof" below).
- The floppy version needs the DIET-packed `IGOR.EXE` to be unpacked and the Borland
  overlay stub table parsed before any of this is possible (see
  [GUIDE_DOSBOX_UNPACKING.md](GUIDE_DOSBOX_UNPACKING.md)). That is real,
  DOSBox-debugger-driven work with no shortcut.

Conclusion: the CD release is strictly easier to reverse engineer and is the correct
starting point. Everything below targets it. Floppy support is deferred to
[REIMPLEMENTATION_PLAN.md](REIMPLEMENTATION_PLAN.md) milestone M11, unchanged.

## Confirmed proof (already executed, reproducible)

Run:

```bash
python3 tools/igor_cd_extract/extract_cd_assets.py
open extracted_cd/EXTRACTION_REPORT.md
```

This reads the 276-entry Spanish-CD resource table recovered by the historical
`scummvm-create-igortbl` project, seeks directly into `IGOR-CD/IGOR.EXE` at each
documented offset, and decodes every entry using formats reconstructed from the
historical ScummVM engine's own resource-loading code (`igor.cpp`) -- **no game code
is executed, no interpreter is involved, this is a from-scratch, from-bytes
reimplementation of each decoder in Python.** The result, as of this writing:

- All 276 catalogued resources fit inside the 9,115,648-byte EXE with unique names
  (zero bounds violations).
- 35/35 backgrounds decode as raw VGA-mode-13h pixel rasters (320 px wide, height =
  size / 320) and visually match real game rooms (verified by eye, e.g.
  `extracted_cd/PhilipRoom/background.png`, `extracted_cd/Park/background.png`).
- 31/31 palettes decode as 6-bit-per-channel VGA DAC triples (values 0-63 confirmed
  by histogram before any interpretation), scaled to 8-bit for display.
- 26/26 masks decode as `{byte value, uint16-LE run length}` RLE covering exactly
  320x144 pixels; rendering each distinct area id as a flat color reveals real scene
  silhouettes (the `Park` room's mask, decoded completely independently of the
  background image, outlines the statue, tree trunk/canopy, and path split visible in
  the background -- see both PNGs side by side).
- 25/25 area-property tables (`BOX_*`) decode as 5-byte
  `{area, object, y1Lum, y2Lum, deltaLum}` records with the original code's invariant
  (`area & 0x80 == 0`) holding for every single entry.
- 28/28 room text resources decode their 320+432-byte perspective-scale header and
  their Spanish-text streams (accented characters un-obfuscated via the historical
  XOR-like byte transform).
- 13 of 96 animation resources (`FRM_`/`ANM_`) use the shared sparse-RLE sprite codec
  (`decodeAnimFrame`); decoded **completely blind, with no frame-offset table**, by
  exploiting the fact that the format is self-delimiting, and independently
  cross-checked against the sibling `AOF_*` frame-offset table for 3 of 5 `ANM_`
  cases -- every single frame offset the from-scratch decoder found matched the
  original table's offsets exactly (see "ANM/AOF cross-validation" in the report).
  `ANM_PhilipVodka` frame 0, decoded and palette-composited purely from these two
  independently-verified formats, is a clean, recognizable sprite of a character.
- The remaining 83 animation resources decode to zero frames under that codec --
  **not a bug**, but proof (confirmed by reading `parts/part_15.cpp`) that several
  rooms' Pascal code uses a bespoke fixed-stride raw sprite sheet instead
  (`_animFramesBuffer + frame*598 + i*26`-style indexing) and never calls
  `decodeAnimFrame` at all. This is the single most important finding of this pass:
  **animation formats are chosen per room in the original code, not globally**, and
  the historical ported C++ is exactly where that per-room stride is recorded.

This means: every static-asset format needed to view and lay out a room (background,
palette, walk/interaction mask, area properties, room text) is **fully solved and
automatable** for the CD release. Sprite/animation formats are **partially solved
generically** (~14%) and **solvable per room by reading already-ported C++** for the
rest. Action/dialogue logic (`DAT_*`) is confirmed opaque and bespoke, exactly as
[REIMPLEMENTATION_PLAN.md](REIMPLEMENTATION_PLAN.md) already assumed.

## The historical table is incomplete, and format knowledge alone recovers what it misses

The 276-entry `resource_sp_cdrom.h` table was hand-built in 2007-2009 by whoever
ported the rooms actually implemented at the time. It is not a catalog of the whole
executable, and it is not even a complete catalog of resources needed by the rooms it
*does* implement: `IMG_ChurchMosaic` / `PAL_ChurchMosaic` / `MSK_ChurchMosaic` are
defined resource IDs, used by the already-ported `parts/part_14.cpp`, and present in
both English-demo tables -- but were simply never added to the Spanish-CD table.
Measuring byte coverage confirms the scale of the gap: **the 276 entries account for
only 29.5% of the 9,115,648-byte EXE (2,690,473 bytes); 70.5% (6,425,175 bytes across
91 gaps) is uncatalogued.** Most of that is legitimate x86 code (each NE segment holds
both a room's logic and its assets), but not all of it -- some of it is more rooms.

`tools/igor_cd_extract/discover_rooms.py` proves this directly, with no resource
table as input at all. Every cataloged room shares one structural signature: a
46,080-byte raw background, immediately followed by an all-<64 VGA palette,
immediately followed by a run-length mask that decodes to exactly 320x144 pixels with
zero leftover bytes. That triple constraint has a vanishingly small false-positive
rate (random bytes essentially never satisfy "all <64 for hundreds of contiguous
bytes" *and* "a 3-byte-record RLE stream that sums to exactly 46080 with zero
clipping"), so scanning the *entire* EXE for it, independent of any table, is both
cheap and reliable. Running it against `IGOR-CD/IGOR.EXE` finds:

- **21 chains matching the known table** (confirms the scanner's signature is correct
  by reproducing entries it was never told about).
- **4 chains confidently renamed** by cross-referencing the *decoded mask byte length*
  (which depends only on scene silhouette, not language or file layout, so it stays
  constant across CD/demo releases) against the two English-demo tables --
  including `ChurchMosaic` at a brand-new CD-only offset, recovered with **zero**
  table entries for the CD release and matching the demo's mask length (2445 bytes)
  exactly.
- **2 ambiguous matches** (mask length collides between two differently-named demo
  rooms; needs a second signal, e.g. palette content or DOSBox comparison, to
  disambiguate).
- **24 completely unnamed, previously uncatalogued rooms**, verified by eye: a
  torch-lit stone corridor consistent with the maze (parts 50-67 have no historical
  C++ and were exactly the rooms expected to be missing from the table), a full
  lecture hall with a professor and students, a swamp/forest exterior, a tower
  entrance at night, and 20 others -- all rendered as clean, complete, recognizable
  scenes purely from format knowledge, with no disassembly and no DOSBox involved.

**This directly answers the risk this plan exists to retire: the reverse-engineered
format knowledge, not the historical hand-built table, is what makes rooms
discoverable, and it already recovers rooms the 2009 project never touched.** The
practical consequence for Phase 1 below: treat `resource_sp_cdrom.h` as a convenient
set of *names* for a subset of resources, not as the authoritative list of what
exists. Run the structural scanner first, use the table (and demo tables, via mask-
length fingerprinting) only to *label* what it finds.

Caveats, honestly stated:

- The scanner only recovers `IMG_`/`PAL_`/`MSK_`/`BOX_` (backgrounds, palettes,
  masks, area tables) via this signature. It opportunistically finds `BOX_` (fixed
  256x5-byte layout immediately after the mask) but does not yet recover `TXT_`
  (variable-length, no fixed anchor to search backward from), `FRM_`/`ANM_`/`AOF_`,
  or `DAT_`/`WLK_` for newly discovered rooms -- those still need Phase 3-5's
  per-room methodology once a room is known to exist.
- Duplicate mask-length matches are possible when the same room is stored twice at
  different game states (`ChurchPuzzle` matched two distinct chains this way, not a
  scanner bug); the tool disambiguates these by offset rather than overwriting one.
- "Unnamed-new" rooms still need a real name and role (which part number, which
  scene) before they're useful for engine work; get that from DOSBox-X (walk there,
  see what part number the debugger reports) or from cyxx's disassembly/call-graph
  output, not from guessing based on the picture alone.


## Reverse-engineering methodology, phase by phase

### Phase 0 — Tooling

Set up once, independent of any room:

- **DOSBox-X** with the integrated debugger, for black-box behavior observation and
  breakpoint/memory-dump work (`brew install dosbox-x`; see
  [GUIDE_DOSBOX_UNPACKING.md](GUIDE_DOSBOX_UNPACKING.md) for the debugger workflow,
  written for the floppy EXE but the debugger techniques apply to the CD EXE too).
- **A disassembler that understands 16-bit NE executables.** The `cyxx/igor` project
  already contains a working, from-scratch NE/segment parser
  (`reference/cyxx/igor/segment_exe.cpp`, `tools/decode_igor/segment_exe.cpp`) that
  recognizes this exact CD executable and emits 81 disassembly units -- use it
  directly rather than re-deriving NE parsing. Where deeper interactive disassembly
  is useful, Ghidra (free) can also load NE executables with recent versions/loaders;
  IDA Free is an alternative if available. Treat the cyxx parser as the primary tool
  since it is already proven against this exact file.
- **Python 3, stdlib only**, for format decoders. Every decoder written so far
  (`tools/igor_cd_extract/extract_cd_assets.py`) uses only `struct`, `zlib`, `json`,
  `re` -- no image library dependency, so there is nothing to install and nothing
  that can silently misinterpret pixel data through a third-party codec.
- **A hex viewer/editor** for spot-checking raw bytes against decoder assumptions
  (plain `xxd`/`hexdump -C` is enough; this plan's proof steps all used it).

### Phase 1 — Resource catalog: scan structurally, use the table only to label

The historical resource table (`reference/scummvm-create-igortbl/resource_sp_cdrom.h`)
was hand-generated in 2007-2009 for the rooms implemented at the time. Treat it as a
**naming aid for a subset of resources**, not as the catalog -- it covers only 29.5%
of the executable and is missing entries even for some already-ported rooms (see
above). The corrected process:

1. Run the structural scanner (`tools/igor_cd_extract/discover_rooms.py`) first. It
   finds every `IMG_`/`PAL_`/`MSK_`(/`BOX_`) chain in the whole EXE from format
   invariants alone, with no table as input.
2. Cross-reference each chain against the CD table (exact offset match -> `known`)
   and, where that fails, against the decoded mask's byte length compared to every
   name across the CD **and both English-demo tables** (`likely-named`) -- masks are
   visual, not language-dependent, so this length is a stable fingerprint across
   releases even when a room's CD-table entry is missing entirely.
3. Parse the CD table itself (see `parse_resource_table()` in the extraction tool)
   for the remaining resource kinds the structural scanner does not yet recover
   (`TXT_`, `FRM_`/`ANM_`/`AOF_`, `DAT_`, `WLK_`) into `{name, offset, size}` triples.
4. Bounds-check every table entry against the live `IGOR.EXE` size (done; zero
   violations) and structurally validate it against its type's invariants (done for
   IMG/PAL/MSK/BOX/TXT; see decode functions and their assert-equivalents).
5. Where the table is silent or wrong for a resource kind the scanner can't recover on
   its own (e.g. `TXT_MainTable`'s alternate layout), re-derive it from the historical
   `igor.cpp`/`part_XX.cpp` call sites rather than guessing, since those files show
   exactly which resource ID is loaded into which buffer and how it is interpreted
   immediately afterward.
6. For a chain the scanner finds that stays `unnamed-new` after step 2, give it a
   real identity (part number, room role) by walking there in DOSBox-X and reading
   the debugger's reported state, or by tracing its segment's disassembly with the
   cyxx NE/overlay parser the same way the original 2009 author did (see
   `reference/cyxx/igor/docs/RE.md`, "Data Files" and "Engine" sections).

This phase is complete for `IMG_`/`PAL_`/`MSK_`/`BOX_` discovery (51 chains found,
27 beyond the CD table) and for the CD table's own 276 named entries. Naming the 24
still-unnamed chains and recovering their `TXT_`/`FRM_`/`DAT_` companions is open work.

### Phase 2 — Static asset formats (background, palette, mask, area table, text)

All five formats are fully reverse engineered and implemented; see the "Confirmed
proof" section above and the decoders in `tools/igor_cd_extract/extract_cd_assets.py`
for the exact algorithms, each traceable line-by-line to its origin in the historical
`igor.cpp` (`loadRoomData`, `decodeRoomMask`, `decodeRoomAreas`, `decodeRoomText`,
`decodeRoomStrings`, `decodeRoomString`, `updatePalette`). Remaining work here is
breadth, not discovery:

- Extend the tool's text decoder to also handle the two known special-cased text
  resources (`TXT_MainTable`, used by `loadMainTexts()` for verb/preposition/global
  object name tables; `TXT_Library2`, parsed with `skipObjectNames=true` in
  `part_33.cpp`) once those rooms are reached, rather than assuming the generic
  320+432-byte-header layout always applies.
- Cross-check a handful of extracted backgrounds pixel-for-pixel against a DOSBox-X
  screenshot of the same room (Milestone M2 in REIMPLEMENTATION_PLAN.md); this is the
  first point where the DOS binary is used as an oracle rather than a byte source.

### Phase 3 — Animation/sprite formats

Two known encodings so far, both empirically confirmed:

1. **Sparse-RLE (`decodeAnimFrame`)**: self-delimiting, concatenated, frame-count-free
   sprite stream. Fully implemented and independently cross-validated against the
   `AOF_*` offset tables (see "Confirmed proof"). Applies to at least
   `ANM_PhilipVodka`, `ANM_PhilipLauraIntro`, `ANM_LauraIntro`, and 10 `FRM_*`
   resources.
2. **Fixed-stride raw sheet**: a plain `width * height` byte block per frame, indexed
   as `buffer + frame * frameSize + row * width`, with the exact `frameSize`/`width`
   constants hardcoded per call site. Confirmed in `parts/part_15.cpp` for
   `TobiasOffice`. This is not a single global format -- each room's ported C++ (or,
   where missing, its disassembly) must be read to find the constants, exactly as
   [REIMPLEMENTATION_PLAN.md](REIMPLEMENTATION_PLAN.md)'s "native per-room workflow"
   already prescribes.

Process per room going forward:

1. Try the generic sparse-RLE decoder first (already automatic in the extraction
   tool); if it yields a plausible frame count with zero leftover bytes, the format
   is solved for that resource.
2. If it yields zero frames, grep the historical `part_XX.cpp` for the resource's
   loaded buffer offset (`_animFramesBuffer + ...`) and read off the literal
   `frame * N + row * W` indexing used by the original port -- this is a direct,
   already-done disassembly-to-C translation, not new reverse engineering.
3. If no historical C++ exists for that room (maze 50-67, plane 76, parts of 75,
   endings 91-94/96-97), fall back to the cyxx disassembly/trap call graph to find
   the equivalent x86 loop and its stride constants, then implement the same
   generic-or-fixed-stride decoder for it.
4. Record the resolved format (generic/fixed-stride/other) per resource name in a
   durable notes file so the production `engines/igor/graphics.cpp` never has to
   redo this discovery.

### Phase 4 — Action, dialogue, and walk-transition logic (`DAT_*`, `WLK_*`)

These are confirmed **not** self-describing formats; they are packed structures whose
field layout is a compile-time constant per room, expressed today as the
`RoomDataOffsets`/`PART_XX_ROOM_DATA_OFFSETS` tables in the historical `igor.h` /
`staticres.cpp`. Do not attempt a generic byte-level decoder for these; instead:

1. Treat each `PART_XX_ROOM_DATA_OFFSETS` entry as an already-reverse-engineered
   schema for that room's `DAT_*` blob (offsets into it for the default/use/give verb
   tables, object-to-object action matrix, dialogue question/reply/matrix regions,
   and the area-to-area walk-transition matrix used by `buildWalkPath()`).
2. Validate each schema against the live blob's size and the historical code's own
   asserts (e.g. `dialogueDataSize <= 500`, `matSize` bounds) before trusting it.
2. For rooms whose C++ is missing entirely, recover the equivalent offsets by
   disassembling the room's action-dispatch switch with the cyxx tools and matching
   its indexing arithmetic against the `RoomDataOffsets` struct shape used elsewhere.
3. `WLK_*` resources are few (4 total, all bridge-cutscene-specific: a per-column
   height lookup and a collision bitmap used only by `PART_05_ACTION_102`) and are
   not a general walkbox system -- there is no classic SCUMM-style polygon walkbox
   format in this game. The real walkable-area system is `MSK_*` (per-pixel area id)
   plus `BOX_*` (per-area object/lighting properties) plus the transition matrix
   inside `DAT_*`; treat these three together as "the walkbox system" going forward
   and do not look for a fourth, simpler format that does not exist.

### Phase 5 — Code/control-flow reverse engineering for rooms with no historical port

Roughly 15% of parts (maze 50-67, plane 76, remaining ending sequences, parts of 75)
have no native C++ in the 2009 snapshot. For these:

1. Use the cyxx interpreter/disassembler to get a clean, already-parsed x86 subset
   (its own author reports the effective instruction subset is small -- "the basic
   switch/case parser is under 700 lines" -- because the Pascal compiler emits very
   literal, macro-heavy, unoptimized code). This is corroborated by
   `reference/cyxx/igor/docs/RE.md`.
2. Run the room in DOSBox-X, driving it manually, and record: entry/exit state,
   resource IDs requested, palette/frame checkpoints, and dialogue/action outcomes.
   This is the authoritative oracle when disassembly is ambiguous.
3. Translate one behavior at a time to ordinary C++ against the shared engine
   systems (never against a re-hosted interpreter), immediately backed by a state
   digest or Event Recorder scenario before moving to the next behavior -- see
   [REIMPLEMENTATION_PLAN.md](REIMPLEMENTATION_PLAN.md)'s "Native per-room workflow"
   and milestone M9, which this phase directly feeds.

## Validation plan (secondary objective)

[REIMPLEMENTATION_PLAN.md](REIMPLEMENTATION_PLAN.md) already specifies a five-layer
verification design (checked resource catalog, canonical state digest, Event
Recorder, unit tests, external oracle comparison) plus a per-part scenario matrix.
This section adds the asset-level layer that sits underneath all of them, now that it
has been demonstrated concretely:

1. **Format-level validation (done, ongoing).** Every decoder asserts its own
   invariants (sizes divisible by record size, bounds, documented flag bits) and
   reports violations instead of silently producing wrong output -- see the
   `EXTRACTION_REPORT.md` bounds/status tables. Extend this same discipline to every
   new format as Phases 3-5 resolve them.
2. **Independent cross-validation where a second source exists.** The `AOF_*` vs.
   self-delimited `ANM_*` frame-offset comparison is the template: whenever two
   independently derived views of the same data exist (a table plus a self-describing
   stream, or a ported C++ routine plus a disassembly), diff them mechanically and
   require agreement before trusting either.
3. **Pixel/byte comparison against DOSBox-X.** For every room, once the engine can
   render it, capture a DOSBox-X screenshot of the same room/state and diff it against
   the engine's indexed framebuffer + palette (not the scaled/backend output). This
   was already planned in REIMPLEMENTATION_PLAN.md's Milestone M2 gate; the
   asset-extraction tool's `background.png`/`mask.png` outputs are the fastest way to
   do a first-pass version of this today, before any engine code exists, by comparing
   them against DOSBox-X screenshots directly.
4. **Canonical state digest, Event Recorder, and oracle comparison** as already
   specified in REIMPLEMENTATION_PLAN.md -- unchanged, and now easier to trust because
   the asset layer underneath them has already been shown to be correct rather than
   assumed.
5. **Per-part scenario matrix** as already specified -- each room's entrances, exits,
   hotspots, actions, and dialogue branches enumerated and checked off against both a
   replay and a focused test, per REIMPLEMENTATION_PLAN.md's "Native per-room
   workflow".

## Immediate next steps

1. Name the 24 `unnamed-new` chains `discover_rooms.py` found (see
   `extracted_cd_discovered/DISCOVERY_REPORT.md`): walk each in DOSBox-X and read the
   debugger's reported part number/state, or trace the segment with cyxx's
   disassembly, and record the mapping. Prioritize the corridor-like backgrounds,
   since parts 50-67 (the maze) have no historical C++ at all and are the most
   likely source of a large cluster of these.
2. Extend `discover_rooms.py` to also recover each new chain's `TXT_` (by scanning
   backward from the `IMG_` start for a plausible 752-byte scale-table boundary) and
   attempt the `FRM_`/`ANM_` sparse-RLE decoder against the segment data preceding
   it, now that Phase 3 shows how to detect success (clean, zero-leftover decode).
3. Extend `tools/igor_cd_extract/extract_cd_assets.py`'s text decoder to handle
   `TXT_MainTable` and `TXT_Library2`'s alternate layouts (Phase 2).
4. Pick 2-3 rooms whose `FRM_*` decoded to zero frames, read their `part_XX.cpp`
   rendering code, and add a second, fixed-stride decoder path to the tool, proving
   Phase 3's methodology on a second format the way it was just proven for the first
   (recommended: `CollegeLockers`, `Laboratory`, or `Park`, all with modest,
   readable historical C++).
5. Capture one DOSBox-X screenshot of a room already extracted here (e.g.
   `PhilipRoom` or `Park`) and pixel-diff it against `background.png` to close the
   loop on Phase 2's remaining validation step.
6. Only after 1-5: begin REIMPLEMENTATION_PLAN.md Milestone M0 (ScummVM fork/branch
   setup). Do not start the engine scaffold before the asset pipeline above is this
   well understood for at least one full room group, per that plan's own risk
   register ("Tests work only through --boot-param").
