## 1. Part 30 — `DLG_CollegeStairsFirstFloor` (id 34)

The shipped catalog had **no row at all** for this dialogue. Part 30's `PART_30_ROOM_DATA_OFFSETS`
in `static_walk.cpp` did have values, but they were wrong (see *Corrections* below).

**Row added:** `{ DLG_CollegeStairsFirstFloor, 0x425fcd, 2753 }`

Derivation:
- Range is cseg111 `+0xECD .. +0x198E`.
- Bounded from both sides: a **byte-identical 2753-byte image** begins at `src + 2753`
  (= seg111:0x198E), which fixes the length exactly.

**Offsets** (`static_walk.cpp`, `PART_30_ROOM_DATA_OFFSETS`, dlg tuple):

```
{ -90, 9, 1489, 11, 30, 0, 2711, 2729, 11 }
```

The engine's addressing (`resource.cpp:153-176`) is, for `_language == 0`:

- question `i`, line `n`: `blob + questionsOffset + (i + 1) * 164 + (n + 1) * 41`
  → `115 + i * 164 + n * 41`
- reply `i`: `blob + repliesOffset + (i + 1) * 102 + _language * 51`
  → `1591 + i * 102`

Blob layout, in full — extents measured by decoding, not estimated:

| Region | Blob offsets | Size |
|--------|--------------|------|
| dialogue matrix | 0 … 114 | 115 |
| 9 question cells, stride 164, two 41-byte lines each | length bytes 115 … 1468; text 116 … 1447 | |
| 11 reply cells, stride 102, 51 B per language | length bytes 1591 … 2611; text 1592 … 2645 | |
| padding | 2645 … 2710 | 66 |
| question sound table | 2711 … 2728 | 18 |
| reply sound table | 2729 … 2752 | 24 |

Note the reply cells are *not* a contiguous 1122-byte run: the stride is 102 but only the first
51 bytes belong to one language, so reply 10's length byte lands at 2611 and its text ends at
2645, leaving 66 bytes of padding before the sound tables.

Sound convention (same as already proven for parts 12 and 17): because the 7th tuple field is
non-zero, `resource.cpp:135-142` uses the **explicit** offsets and skips the legacy fallback
that derives them from `dataSize`. So `questionSoundsOffset = 2711` and
`replySoundsOffset = 2729` are passed in directly, entry `i` is read at `+(i + 1) * 2`, and the
word *at* the offset itself is a non-indexed residue.

- residue at `blob + 2711` = `0xfcf8`
- question sounds: `460 461 462 _ 463 464 465 466 467`
- residue at `blob + 2729` = `0x01d3` = **467** — i.e. it aliases question 8's own word
- reply sounds: `468 469 470 471 _ 472 473 474 475 476 477`
- reply 10 reads `477` at `blob + 2751`, landing exactly on the 2753-byte end

(For reference, the legacy fallback at `resource.cpp:139-140` would have derived
`questionSoundsOffset = 2753 - (9 + 11 + 2) * 2 = 2709` and `replySoundsOffset = 2731` — both
wrong for this blob. That is precisely why the explicit values are supplied.)

Verified by replaying `loadDialogueData`'s arithmetic against the real blob: all 9 question
slots and all 11 reply slots land on plausible length-prefixed Spanish cells (a few line slots
are legitimately empty), and the sound tables come out exactly as tabulated above.
`decodeRoomString` then remaps the game's high-byte codes (e.g. `0xA3 → 0xC3`) to CP437
accents — so raw code-page dumps look like mojibake, which is expected and not a defect.

## 2. Part 23 — `FRM_CollegeCorridorLucas1..4` (ids 79–82)

**Method.** These live in cseg127, which begins with a resource-loader stub at `+0x0002`.
Note: a segment's **leading word is its segment number, not a stub length** (cseg127's is
`0x007F` = 127, for a 0xD4-byte stub).

Each block is:

```
mov di, SRC            ; resource offset within this segment
  ... far-pointer relocation resolve (cmp es:[0],0x3fcd) ...
push es / push di      ; source
  <destination setup>
push LEN               ; <-- the length
lcall
```

Decoding cseg127's first stub gives four blocks, whose source offsets *and* lengths form exact
contiguous chains (`0xd6+0xa20 = 0xaf6`, `0xaf6+0x4c9 = 0xfbf`, `0xfbf+0x1950 = 0x290f`).

**Rows added:**

| Id | Name | File offset | Size | src | len |
|----|------|-------------|------|-----|-----|
| 79 | `FRM_CollegeCorridorLucas1` | `0x4ae9d6` | 2592 | 0x0d6 | 0xa20 |
| 80 | `FRM_CollegeCorridorLucas2` | `0x4af3f6` | 1225 | 0x0af6 | 0x04c9 |
| 81 | `FRM_CollegeCorridorLucas3` | `0x4af8bf` | 6480 | 0x0fbf | 0x1950 |
| 82 | `FRM_CollegeCorridorLucas4` | `0x4b120f` | 1140 | 0x290f | 0x0474 |

**Confirmed three independent ways** (this is why I trust them despite no runtime test):

1. **Destination offsets match the engine.** The stub's cumulative `add di` values are
   `0x0000 / 0x0a20 / 0x0ee9 / 0x2839` — exactly the `loadOffset` values ScummVM's
   `loadAnimData({FRM_1,FRM_2,FRM_3,FRM_4})` computes when concatenating in id order.
2. **Control rooms reproduce their catalogued sizes exactly.** SharonMichael (cseg121) yields
   3630/7752/5676/6762; Caroline (cseg124) yields 25080/270/7595. Note Caroline's *file* order
   is 1, 3, 2 — so source file order is *not* id order, but stub block order **is** id order.
3. **The second stub in cseg127 was already catalogued.** The stub at `+0x2D83` decodes to
   `0x4b16f4/24` and `0x4b170c/4410`, which are *already* in the catalog as
   `FRM_SpringBridge1` / `FRM_SpringBridge2` — exact offset and size agreement.

Also established: that second stub is SpringBridge's data, **not** part 23. Part 23's loader
(`cseg126:1AFC-1B0F`) only calls `cseg128:0x0002` and `cseg127:0x0002`.

Part 23 needs exactly 10 ids — `DAT`, `FRM1..4`, `TXT`, `IMG`, `PAL`, `MSK`, `BOX` — and only
the four FRMs were missing. Total anim payload 11437 bytes, well inside the buffer.

## 4. Part 28 — ASAN `heap-buffer-overflow` in `PART_28_HELPER_5`

**Fixed:** `_gameState.unk10 = 1;` added to `PART_28()`, immediately before the
`_currentPart == 280 / 281` dispatch.

The reported crash was a 1-byte read in
`part_28.cpp:258` (`PART_28_HELPER_5`), reached from `PART_28_UPDATE_ROOM_BACKGROUND()`:

```cpp
_screenTempLayer[i * 100 + j] = _animFramesBuffer[(frame - 1) * 1320 + i * 30 + j];
```

**Ruling out the obvious suspects first.** `_animFramesBuffer` is `malloc(65535)`
(`igor.cpp:53`), and Caroline's three FRMs are concatenated to only 32945 bytes by
`loadAnimData()` (offsets `0`, `25080`, `25350`). The buffer is not too small, so the index
must be negative — i.e. `frame == 0`, and `unk10` is what supplies `frame`.

**Decoding the helper (cseg123:0x00B7–0x00D5).** Raw bytes `8a 46 06` are
`mov al, [bp+6]`, i.e. a **load of the frame parameter**, not the store that the hand-written
listing in `code/123_2C8A.asm` renders as `mov.b r0.b.l, s2:r5.w+6`. That listing mis-renders
loads as stores in several places (the same mistake appears at cseg123:01BA/01D7). Decoded
correctly, the routine is:

```
mov cx, [0xEB22]          ; j
imul ax, [0xEB20], 0x1E   ; i*30
mov dx, ax
mov al, [bp+6]            ; frame        <-- overwrites the low byte of i*30
xor ah, ah
imul ax, ax, 0x528        ; frame * 1320
les di, [0xD162]          ; anim base
add di, ax / add di, dx / add di, cx
mov dl, es:[di-0x528]     ; read animBase + frame*1320 + i*30 + j - 1320
```

which is exactly `_animFramesBuffer[(frame - 1) * 1320 + i * 30 + j]`. So the C++ is faithful and
**the frame is 1-based**; `frame == 0` genuinely reads 1320 bytes before the buffer. The bug was
a missing initialisation, not a wrong formula.

**Locating the original's initialisation.** `sub_123_01A2` is the room-background update; it
matches `PART_28_UPDATE_ROOM_BACKGROUND()` instruction for instruction
(`cmp.b [0xEACA],0x3D` = `compareGameTick(61)`, `cmp.b [0xEB2C],0x2`, `cmp.b [0xEB2C],0x6`,
`getRandomNumber(7)` → counter 3). So the counter is **`s3:0xEB2C`**, and `s3:0xEACA` is the game
tick, not the counter. `0xEB2C` is written in exactly one place in the whole segment:

```
cseg123:2E04  mov.b s3:0xEB2C, 0x1
```

inside part 28's room setup, before the state dispatch (`cmp.w r0.w,0x118` / `0x119` = states
280/281). Our port had no corresponding write anywhere in `part_28.cpp`, which is the whole bug.
The placement mirrors the original: unconditional, immediately before the dispatch.

## 5. Part 21 — `DLG_CollegeCorridorMargaret` (id 89)

**Row added:** `{ DLG_CollegeCorridorMargaret, 0x4c7973, 6980 }`

> **Correction (later the same day).** This row was first added with size **6982**, on the
> reasoning below. That was wrong, and so was the reasoning: it leaned on
> `resource.cpp`'s derived sound-table formula, which turned out to be off by one word
> (see section 6). With the formula corrected the size is **6980**, and every speech index
> decodes cleanly. The offset `0x4c7973` was correct throughout.

Part 30's method does transfer, but only if you find the *dialogue-loader* segment rather than a
resource-stub segment. Margaret's `DAT` at `0x4c2ff1` sits in cseg129, but the dialogue lives in
the **next** segment, exactly as part 30's does:

| Room | Code seg | Dialogue-loader seg | Loader prologue |
|------|----------|---------------------|-----------------|
| Part 30 | cseg110 | cseg111 | `b8 06 00 9a ff ff 00 00 83 ec 06` |
| Part 21 | cseg129 | **cseg130** | `b8 06 00 9a ff ff 00 00 83 ec 06` (identical) |

**Offset.** The dialogue offset is a repeated immediate in the loader segment. Counting
`mov` immediates in each segment reproduces part 30's known value and gives Margaret's:

| Segment | Top immediate | Count | Other repeats |
|---------|---------------|-------|---------------|
| cseg111 | `0x0ECD` | 29 | `0x03C9`×3, `0x0540`×3, `0x0542`×3, `0x00A0`×2, `0x0082`×2 |
| cseg130 | `0x0F73` | 30 | `0x03C9`×3, `0x0540`×3, `0x0542`×3, `0x00A0`×2, `0x0082`×2 |

The near-identical secondary profile is a strong independent check that cseg130 is the same kind
of segment. So the blob is `cseg130 + 0x0F73 = 0x4c7973`.

**Size — originally mis-derived as 6982; the correct value is 6980.** A 64-byte duplicate of the
blob head appears at `0x4c94b7`, which suggests `6980`. I first rejected that and chose `6982`,
because `questionSoundsOffset == 0` makes `resource.cpp` derive the tables from `dataSize`, and at
6980 the first question sound came out as `64505`. That reasoning was circular: `64505` was not
evidence about the size, it was evidence that the *formula* was wrong. The tail layout proved by
the four rooms that carry original offsets (section 6) is:

```
questionSoundsOffset = dataSize - (questionsSize + repliesSize + 1) * 2
replySoundsOffset    = questionSoundsOffset + questionsSize * 2
```

which gives `qS = 6980 - 122 = 6858`, `rS = 6858 + 20 = 6878`, and
`rS + (50 + 1) * 2 == 6980` exactly. Structure checks against part 21's tuple
`{ -85, 10, 1658, 50, 30, 0, 0, 0, 0 }`:

- matrix = `-85 + 205 = 120` bytes; question `i` line `n` at `-85 + (i+1)*164 + (n+1)*41`
- reply `i` at `1658 + (i+1)*102`; 10 questions, 50 replies, both within
  `MAX_DIALOGUE_QUESTIONS` (30) and `MAX_DIALOGUE_REPLIES` (100)
- 9 non-empty question cells (all in line slot 1), 13 non-empty replies
- 0 out-of-range or overrunning cells
- all text sits in language slot 0, which is correct: `igor.cpp:123` sets `_language = 0`, and this
  Spanish build ships a single language per blob

## 6. Dialogue speech tables — engine formula and `PART_08`

While collecting the speech indices (asked for after the fixes above) two more real bugs turned
up, both in the speech/sound half of the dialogue data.

**The derived fallback was off by one word.** `resource.cpp` computed, for rooms with no explicit
offsets:

```cpp
questionSoundsOffset = dataSize - (questionsSize + repliesSize + 2) * 2;   // 2 too low
replySoundsOffset    = questionSoundsOffset + (questionsSize + 1) * 2;      // accidentally right
```

The four rooms that *do* carry original offsets (parts 6, 12, 17, 30) all satisfy a different
relation, without exception: `replySoundsOffset == questionSoundsOffset + questionsSize * 2`. The
reply table's residue word **is** the last question entry, so the reply entries start two bytes
past it, not four. Consequences of the old formula:

- `questionSoundsOffset` was one word too low, so **question 0's sound index was the residue
  word** — a text byte pair, not an index. For part 17 that is `63483`, for part 21 `64505`.
- `playSound()` asserts `num < _soundOffsetsCount` (`sound.cpp`), so asking question 1 in either
  room would abort a debug build.
- `replySoundsOffset` came out right by two errors cancelling, which is why the bug survived.

Fixed in `resource.cpp`. Both derived rooms now decode cleanly (part 17 `qS=951 rS=961`,
part 21 `qS=6858 rS=6878`), and all five dialogue rooms end with `rS + (rSS+1)*2 <= dataSize`.

**`PART_08_ROOM_DATA_OFFSETS` had its two sound offsets swapped.** It read
`questionSoundsOffset = 15548, replySoundsOffset = 15488`. The blob shows the opposite order: the
first run is `176..197` at `blob+15490`, the second is `200..` at `blob+15550`. Every other room
stores questions before replies with contiguous numbering (part 30: questions 460–467, replies
468–477; part 6: 491–516 then 517–544; part 12: 802–809 then 810–827), so questions must be the
*first* run. Corrected to `qS = 15488`, `rS = 15548` — and `15488 + 30 * 2 == 15548`, matching the
convention. The old values made questions and replies read each other's table.

**Speech indices, all five dialogue rooms** (blob value `0` = no speech; engine index is
`value + 100`, per `playSound()`'s `--num; num += 101`; 1400 sound entries, so valid blob values
are 0–1299):

| Room | Source | qS / rS | Question indices | Reply indices |
|------|--------|---------|------------------|---------------|
| Part 6 SpringPhotographer | explicit | 15458 / 15518 | 491–516 (26 used of 30) | 517–544 (25 used of 35) |
| Part 8 DeanPepperOffice | explicit | 15488 / 15548 | 176–197 (22 used of 30) | 200–232 (21 used of 30) |
| Part 12 OutsideChurch | explicit | 5230 / 5260 | 802–809 (8 used of 15) | 810–827 (18 used of 25) |
| Part 17 OutsideCollege | derived | 951 / 961 | 650–654 (5 of 5) | none (1 slot, unused) |
| Part 21 CollegeCorridorMargaret | derived | 6858 / 6878 | 1199–1207 (9 used of 10) | 1208–1216 (9 used of 50) |

Two rooms are *not* live dialogue rooms and were not touched: part 30's
`loadDialogueData(DLG_CollegeStairsFirstFloor)` call is commented out at `part_30.cpp:113` (its
offsets 2711/2729 do satisfy the convention), and parts 15 and 33 carry tuples but never call
`loadDialogueData`.

## Corrections to mistakes made earlier in this session

Worth recording, because they are the traps in this workflow:

1. **`DLG_CollegeStairsFirstFloor` offset.** I first used `0x426040` with text offsets
   `-205 / 1374 / 2596 / 2614`. Both were wrong. Corrected to `0x425fcd` and
   `-90 / 1489 / 2711 / 2729`. The giveaway was a 115-byte run at the blob start that had
   been misattributed to a trailing reply-graph block.
2. **"No missing ids."** False. That scan globbed only `part_*.cpp`, *and* the regex used a
   capturing group, so `re.findall` returned bare prefixes (`'DAT'`, `'FRM'`) instead of full
   names — the scan was silently near-empty. Re-run with `(?:...)` and a full `**/*.cpp` glob.
3. **"cseg125 is not a resource stub."** Wrong; see part 28 above.
4. **Segment leading word.** Assumed to be the stub length. It is the segment number.
5. **`code/*.asm` renders some loads as stores.** `mov al, [bp+6]` is printed as
   `mov.b r0.b.l, s2:r5.w+6`, which reads as a pointless store. Trust the raw bytes (here
   `8a 46 06`) over the listing's operand order. Getting this backwards is what made the
   part-28 helper look like it computed `(i*30 & 0xFF) * 1320` instead of `frame * 1320`.
6. **The duplicate-image boundary is not always the resource length.** For Margaret's dialogue it
   read 6980 where the true length is 6982, because the tail is zeros in both copies. Always
   cross-check the length against the consumer's own size-derived layout.
7. **Do not validate a resource length against code that is itself unverified.** Margaret's
   dialogue size was "confirmed" at 6982 using `resource.cpp`'s derived formula, then the
   formula turned out to be wrong and the size was 6980. The bogus `64505` index that started
   this was a bug report about the *engine*, not evidence about the *data*. When a decode looks
   wrong, check the decoder against a known-good case before resizing the input.
8. **Check that two related fields are not swapped.** `PART_08`'s `questionSoundsOffset` and
   `replySoundsOffset` were each other's values; the blob's ascending run order is what gave it
   away.
9. **`IGOR.TBL` is big-endian**, so adding a row shifts the header's strings/sounds offsets and a
   naive byte diff points at the wrong place. Parse the tables instead of diffing bytes.
